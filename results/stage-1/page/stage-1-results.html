Pair 1 · Store chunk page numbers as integers, keeping every existing row

Change A
What changes for users
Users see no change in how answers or citations look. Page and slide numbers are now stored in the database as numbers, so page 10 sorts after page 2. The database now rejects a page number below 1.
How
It adds a new migration file numbered 0005 (a migration is a script that changes the database's structure). The script first checks every existing page value against a pattern of digits only, with at least one non-zero digit, and stops if any row fails. It then converts the column to numbers and adds a rule (a check the database enforces on every save) that the value must be 1 or more.
Choices it made
On bad existing data it stops with its own message, which gives how many rows are bad and the ID and value of one of them; nothing is changed. It treats values with a space, a plus sign, a decimal point, or only zeros as bad, and accepts leading zeros ('007' becomes 7). On later runs it skips the conversion and adds the rule only if it is missing. The page-reading code now passes the stored number through without converting it again.
Beyond the ticket
Nothing outside the ticket. Its comment updates include one in scripts/ask_smoke.py, a test script, where only the descriptive comment changed.
Size
8 files. About 35 lines of database script plus 18 lines of comments, and about 15 changed lines in the Python code, mostly comments. It adds one new test file with 6 tests that run as 13 cases: conversion and re-run, 7 kinds of bad value, fixing a bad row and re-running, a brand-new database, inserting page 0 or -1, and confirming the three old migration files are unchanged. It updates 2 existing tests from text to number.
Change B

Pair 2 · A request that fails validation can crash the error reply or get echoed back whole

Change A
What changes for users
A request with bytes that are not readable text now gets the usual 422 'validation' reply with its list of field problems instead of a 500 server error. Any text an error reply repeats back is now cut to 512 characters, so a 2,000,000-byte request gets a reply under 4 KB.
How
Just before an error reply is turned into text, a step walks through every piece of it: unreadable bytes become text with a replacement symbol (�) for each bad byte, and any text longer than 512 characters keeps its start and ends with a note like '...[truncated from 2000000 chars]'. The same step also runs once earlier on the validation error list, so the bytes are fixed before the stage that used to crash on them.
Choices it made
The limit is a setting named MAX_ERROR_ECHO_CHARS (512). It applies to every piece of text in every error reply, including the human-readable 'message' line and field names, not only the echoed values. The length note uses plain digits with no commas. If the limit were ever set below the length of the note, the result is still cut to the limit. Two very long field names that match in their first 512 characters merge into one.
Beyond the ticket
It rewrote the existing explanatory comments on two parts of the error-reply code, and it added two paragraphs to the design document.
Size
Five files: two product code files, one design document, one new test file, and the settings file. About 30 lines of product logic plus about 90 lines of comments. 19 new tests (22 counting variations).

Pair 4 · Stop one owner from creating two classes with the same name

Change A
What changes for users
When an owner tries to create a class with a name they already use, the product refuses, writes nothing, and the app shows a 409 "class_name_taken" error (409 is the standard web code for a conflict with existing data). The message reads: "You already have a class with this name. Pick a different name, or upload to the class you already have."
How
Before saving, it looks up all of the owner's class names and compares each to the new one. It first takes an "advisory lock", a temporary hold in the database that makes a second create from the same owner wait until the first has finished, so two quick taps cannot both get through.
Choices it made
Two names count as the same if they differ only in upper/lower case or in spacing (extra, leading, trailing or tab spaces), so "Biology 101" and " biology 101 " match but "Biology-101" does not. What changes for users
When an owner tries to create a class with a name they already use, the product refuses, writes nothing, and the app shows a 409 "class_name_taken" error (409 is the standard web code for a conflict with existing data). The message explains that names differing only in letter case or spacing count as the same, and suggests picking a different name or using the existing class.
How
Before saving, it looks up the owner's class names, oldest first, and compares each to the new one. It first takes an "advisory lock", a temporary hold in the database that makes a second create from the same owner wait until the first has finished, so two quick taps cannot both get through.
