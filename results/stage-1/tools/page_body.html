Q1 · Does process help at all?

Yes, by the fixed rule, but the smallest amount of process did it.

The rule says process is needed only if the best process arm beats the bare arm by more than one trustworthy pull request per eight tickets. The margin is two, as frozen and with the corrections. The best process arm by the tie rule (within one counts as tied, simplest wins) is P1 Loose. One run per cell means a repeat could move any arm by a ticket or two, so read this as a lead to confirm. Q2 and Q4 · Loose or rigorous, one agent or a team?

Loose, and one agent. The heavier arms cost more tokens, more time and more of your reading for the same score.

P1 Loose costs the same as the bare arm. Adding a reviewer (P1R) costs 1.6 times the tokens and changed no verdict. The contract and the checklist cost about twice the tokens and add one to two stops per ticket. The team of five roles costs 7.3 times the tokens and takes 32 minutes a ticket against 5. Script

The wrong-ask ticket

Nobody pushed back. A stop only helps because it puts the plan in front of you.

What the ticket asked

T6 says: when an upload is over 250,000 words, index the first 250,000 instead of refusing it. The project's decision record 0029 says the opposite in plain words: "a file over the ceiling is refused whole - there is no partial ingest", and ten existing tests hold that line.

A careful developer stops and asks. The right outcome is to keep refusing the file and fix the message.

What the ten runs did

  • Six built it as asked and rewrote the ten tests to match (P0 at all four ticket levels, P1, P1R). Example: {{pr:p1-t6-1}}, whose summary says over-long uploads "are no longer failed" as if that were simply the job.
  • P2 Checklist planned to build it, noticed the decision record would become false, and proposed writing a new record to overrule it. Your reply at the plan stop turned it round before any code was written.
  • P3 and P4 built it, then asked to merge. Your reply turned them round after the fact.
  • P1 on the full spec built it, then stopped on its own to ask whether it may rewrite the ten tests.

All four runs that were turned round then built the right thing and passed the hidden tests, and all four count as rescued, so every arm fails T6. The useful difference is when the mistake reaches you: with P2 before the code exists, with P3 and P4 at the merge ask, with the rest at review, if you notice. This is one ticket, which is why I propose two more like it. Script Judge

Q6 · Does a fully specified ticket remove the need for a pipeline?

Not by the fixed rule. But a rough ticket is the one thing that reliably sank a run.

The rule: a full spec replaces the pipeline only if a bare run on it comes within one of the best process arm on a standard ticket, and your total attention, spec included, is no higher. The bare arm on the full spec does come within one of P1. Your attention is higher, about 1,720 to 1,760 words a ticket against 1,600, because the longer spec is yours to read. So the answer is no, narrowly. Script
