What I would change in the charter

Ranked by how much each one moves the goal: pull requests you can trust, for little of your attention. The first four matter. The rest are housekeeping.

Biggest
Change 1

Treat stage 1 as a first cut, then confirm before deciding

Charter saysEach arm runs once on 8 tickets. Four of your six questions are decided from that, and "within one PR" counts as a tie.
The problemEight single runs are noisy. Two arms that are truly equal, each passing about 6 in 10, still land 2 or more PRs apart about 4 times in 10. Script This is race 1's "one lucky run flips the result" again.
What I'd doLabel stage 1 results provisional. Drop an arm at stage 1 only if it trails by 3 or more of 8. At gate 2, propose a confirm round: the two arms the verdict turns on run twice more on all 8 tickets. With 24 runs each, a gap that size appears by luck about 1 time in 10.

Cost now: none. The confirm round (32 runs) is priced at gate 2, and it doubles as the baseline stage 2 needs anyway.

Medium
Change 2

Runs get three GitHub commands, not open access

Charter saysHidden tests and the answer key stay out of reach.
The problemAll runs share one lab repo. A run could read another run's finished PR for the same ticket. A run on the rough ticket could read the full-spec version. A replay run could look up the real fix, because grounded-class-tutor is public. Script
What I'd doEach run can only: read its ticket, open or update its own PR, and read that PR's checks. Tickets are files in the sandbox, not GitHub issues. Web access is off. Every transcript is scanned, and a run that got around the block is thrown out.

Trade-off: a little less like your real setup, where the checklist reads the issue from GitHub. It is the same for every arm.

Medium
Change 3

Every run starts in a clean room

Charter saysThe bare arm gets the ticket and "open a pull request". Nothing else.
The problemYour work-ticket, triage and file-issue skills load into every Claude session on this Mac. Script A "bare" run would see today's checklist and might follow it.
What I'd doEach run starts with empty Claude settings. The arm's own files are the only instructions it gets. The guard that protects your GCT checkout is added back for every arm.
Medium
Change 4

The script pastes stand-in replies, and judging is split in two

Charter saysA blind judge picks each reply and I paste it. One blind judge scores quality from the diff and the brief.
The problemI know which arm each run is, so I shouldn't be in the reply loop. And a brief gives its arm away: a contract table looks nothing like a two-line PR note.
What I'd doThe harness pastes the judge's chosen reply word for word and logs it. I audit every non-default reply and 1 in 5 of the rest. Code quality is judged from the diff alone. Honesty is judged separately, against script facts.

The rest of what gets frozen

Decision rules

Your six rules stay word for word: ties go to the simpler arm; process is needed only if it beats bare by more than one PR in 8 or bare needs more rescues; a habit add-on must improve two measures for under 30% more cost; Fable builds only for one more PR in 8 or 30% fewer correction rounds; a full spec replaces the pipeline only within one PR and at no more of your attention; the winner must hold within one PR on other codebases.

Added by this page: stage 1 verdicts are provisional until confirmed (change 1), plus the small rules in the table above. On the vague ticket, the open question has one fixed owner answer, given whenever a run asks. A run that guesses right still passes, but is tagged as a guess.

The stand-in owner

  • A run stops with a question. The harness removes the arm's name.
  • A separate judge picks one reply from the frozen sheet.
  • Default reply: "Go with your recommendation and stay in scope."
  • Fixed exceptions: a real problem raised, an edit to an applied migration, an out-of-scope change, the vague ticket's open question, a request to merge or label.
  • The exact wording is written with the tickets and frozen with them.

One sandbox per run

  • Its own copy of the lab repo at the ticket's starting commit.
  • Its own Postgres database. GCT's tests need a real one, and yours is running. Script
  • Its own scratch folder and branch prefix, like p3-t4-1/.
  • Clean Claude settings, three GitHub commands, no web.
  • A token ceiling and a full transcript kept on the Mac.
