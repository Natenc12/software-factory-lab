# A column named `top` breaks Snowflake and Oracle queries

## Problem

In Snowflake, `TOP` is not a reserved word, so `top` is a perfectly good column or table name. sqlglot
reads it as the start of a `TOP n` row limit instead. Reproduced on the current code:

```python
import sqlglot

sqlglot.parse_one("SELECT top FROM t", read="snowflake")
# ParseError: Required keyword: 'expression' missing for <class 'sqlglot.expressions.query.Limit'>.

sqlglot.parse_one("SELECT top.x FROM t AS top", read="snowflake")
# same ParseError

sqlglot.transpile("SELECT top, x FROM t", read="snowflake", write="snowflake")
# ['SELECT FROM t LIMIT x']   (no error, the whole select list is gone)

sqlglot.transpile("SELECT top(5), x FROM t", read="snowflake", write="snowflake")
# ['SELECT FROM t LIMIT 5, x']
```

Oracle has no `TOP` clause at all, and it shows the same problems:
`sqlglot.transpile("SELECT top, x FROM t", read="oracle", write="oracle")` gives
`['SELECT FROM t FETCH FIRST x ROWS ONLY']`, and `SELECT top FROM t` fails to parse.

## Why it matters

A query that uses an ordinary column name either fails, or, worse, comes back as a different query
with its select list silently turned into a row limit. Anyone translating real Snowflake or Oracle
SQL with a `top` column gets wrong SQL and no warning.

## Scope

**In**
- How Snowflake and Oracle read `top` / `TOP`.
- Tests.

**Out**
- T-SQL, Teradata and Redshift, which do have a `TOP` clause (including `TOP (expr)` in T-SQL and
  `TOP` with a bind parameter in Redshift). Their behaviour stays exactly as it is today.
- How a `TOP` row limit is written out in any dialect.

## Decisions

- **Snowflake:** `TOP` is a row limit only when it is followed directly by a plain number, as in
  `SELECT TOP 5 x FROM t` (Snowflake only allows a non-negative integer constant there). In every other
  position `top` is an ordinary name. `top(...)` with parentheses is a function call, kept as written.
- **Oracle:** there is no `TOP` clause, so `top` is always an ordinary name, and `top(...)` is a
  function call.

## Done when

- [ ] In Snowflake, `SELECT top FROM t`, `SELECT top.x FROM t AS top` and `SELECT top, x FROM t` read
      and write back unchanged, and `SELECT top:field FROM t` writes back as
      `SELECT GET_PATH(top, 'field') FROM t`.
- [ ] In Snowflake, `SELECT TOP(x) FROM t` and `SELECT TOP(5), x FROM t` read as function calls and
      write back unchanged.
- [ ] In Snowflake, `SELECT TOP 5 x FROM t` still writes back as `SELECT x FROM t LIMIT 5`.
- [ ] In Oracle, `SELECT top FROM t`, `SELECT top, x FROM t` and `SELECT TOP(5), x FROM t` read and
      write back unchanged.
- [ ] Redshift still writes `SELECT TOP 1 x FROM y` and `SELECT TOP %s x FROM y` as
      `SELECT x FROM y LIMIT 1` and `SELECT x FROM y LIMIT %s`; T-SQL still writes
      `SELECT TOP 5 x FROM t` and `SELECT TOP (@n) x FROM t` unchanged.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] Every existing test passes.
