# The optimizer changes query results for a correlated `IN` that is not a plain filter

## Problem

`optimize()` (through its `unnest_subqueries` step) rewrites a correlated `IN (subquery)` into a
`LEFT JOIN` plus `ARRAY_ANY`. When the join finds no match, the rewritten expression is `NULL`, but
`x IN (<subquery that returns no rows>)` is `FALSE`. That makes no difference when the `IN` simply
filters rows, but it changes the answer anywhere else the difference between `FALSE` and `NULL` shows.

Reproduced on the current code with DuckDB (already a dev dependency):

```python
import duckdb
from sqlglot.optimizer import optimize

con = duckdb.connect()
con.execute("CREATE TABLE t1(a INT, b INT); INSERT INTO t1 VALUES (1,2),(2,3),(NULL,NULL)")
con.execute("CREATE TABLE t2(a INT, x INT); INSERT INTO t2 VALUES (1,10),(2,3)")
schema = {"t1": {"a": "INT", "b": "INT"}, "t2": {"a": "INT", "x": "INT"}}

sql = "SELECT a, b FROM t1 WHERE (a IN (SELECT a FROM t2 WHERE t2.x = t1.b)) = FALSE"
print(con.execute(sql).fetchall())
# [(1, 2), (None, None)]
print(con.execute(optimize(sql, schema=schema, dialect="duckdb").sql("duckdb")).fetchall())
# []
```

The same goes wrong for `SELECT a IN (<correlated>)` in the select list (`NULL` instead of `FALSE`),
`COALESCE(a IN (<correlated>), TRUE)`, `NOT (a IN (<correlated>) AND a > 0)`, and
`(a = ANY (<correlated>)) = FALSE`. A `NOT` placed directly on the `IN` is already handled correctly
today; the other shapes are not.

## Why it matters

The optimizer must never change what a query returns. People run its output in production, and this
one returns different rows with no warning.

## Scope

**In**
- The optimizer's handling of correlated `IN (subquery)` and `= ANY (subquery)`.
- Tests.

**Out**
- Uncorrelated subqueries, `EXISTS`, and scalar subqueries, which are not part of this report.
- The optimizer's other steps.

## Decisions

- An optimized query returns exactly the rows the original returns, wherever the correlated `IN` or
  `= ANY` appears: in the select list, under `NOT`, compared with `= FALSE`, tested with `IS NULL`,
  inside `COALESCE`, in `ORDER BY`, in `HAVING`, `QUALIFY` or a join's `ON`, or combined with other
  conditions by `AND` / `OR`.
- A correlated `IN` used directly as a filter in `WHERE`, alone or combined with other conditions by
  `AND`, is still unnested as it is today: that rewrite is the point of the step, and it is safe there.

## Done when

- [ ] The query above returns `[(1, 2), (None, None)]` after `optimize()`, as it does unoptimized.
- [ ] For each of the shapes listed under Decisions, with both `IN` and `= ANY`, the optimized query
      returns the same rows as the original on DuckDB, including for rows where the subquery finds
      nothing and rows where it finds only `NULL`s.
- [ ] `SELECT x.a FROM x WHERE x.a IN (SELECT y.b FROM y WHERE y.c = x.a)` is still optimized into a
      query with no `IN` left in it.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] Every existing test passes.
