# Allow our subdomains in `cors()` and `csrf()` without writing a function

## Problem

Our front ends live on many subdomains (`https://app.example.com`, `https://admin.example.com`, one
per customer, and more each month). Both `cors()` and `csrf()` take `origin` as a string, a list of
strings or a function, and a string is compared exactly. So today every app either lists every
subdomain by hand, and breaks when a new one appears, or writes its own matching function, and those
functions keep getting it wrong (one of ours accepted `https://app.example.com.evil.net`).

## Why it matters

Allowing "our subdomains" is the most common origin rule there is. The framework should get it right
once, in both middlewares, so apps stop hand-rolling it.

## Scope

**In**
- `cors()` (`src/middleware/cors/`) and `csrf()` (`src/middleware/csrf/`): an allowed-origin string
  may be a pattern, both as `origin: 'https://*.example.com'` and as an entry of a list mixed with exact
  origins.
- Their JSDoc; tests.

**Out**
- `origin` given as a function: it keeps full control, unchanged.
- `cors()`'s `origin: '*'` (any origin): unchanged.
- Patterns anywhere but the start of the host (`https://app.*.com`, `https://example.*`): such a string
  is compared exactly, as today.
- `csrf()`'s `secFetchSite` option, and every other option of both middlewares.
- The separate packages under `adapters/`.

## Decisions

- A pattern is an origin whose host starts with `*.`: `<scheme>://*.<rest of host>[:<port>]`. Every
  other string is compared exactly, as today.
- When `cors()` allows an origin through a pattern, it answers with that request's origin in
  `Access-Control-Allow-Origin` (never the pattern itself) and adds `Vary: Origin`, as it does for an
  exact origin today. Preflight requests work the same way.
- When `csrf()` allows an origin through a pattern, the request goes through; otherwise it is refused
  with 403, as today.
- **Not yet decided:** exactly which origins `https://*.example.com` matches: what `*` may stand for,
  and how the bare domain, the scheme and the port are treated.

## Done when

- [ ] `cors({ origin: 'https://*.example.com' })` answers a request from `https://app.example.com`
      with `Access-Control-Allow-Origin: https://app.example.com`.
- [ ] `csrf({ origin: 'https://*.example.com' })` lets a form POST from `https://app.example.com`
      through.
- [ ] A list mixing patterns and exact origins works in both.
- [ ] Origins the pattern must not match are refused, including `https://app.example.com.evil.net` and
      `https://evil-example.com`.
- [ ] Tests for each case; every existing test passes.
- [ ] `pnpm test` passes (after `pnpm run build`), and `pnpm run lint` and `pnpm run format` are clean.

## Notes for the implementer

- Tests for both middlewares sit beside them; `app.request(url, { headers: { Origin: ... } })` drives
  them without a server.
- Install with `pnpm install`, build with `pnpm run build` (the tests in `build/` need it), then run
  `pnpm test`. A single folder runs with `pnpm exec vp test --run src/middleware`.
- The Node adapter's "Should call onAbort" tests (`runtime-tests/node`) are timing-sensitive and can
  fail on a busy machine; that is known and not part of this ticket.
