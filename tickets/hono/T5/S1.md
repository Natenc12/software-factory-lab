# Client: a signal set both on the client and on a request makes the request fail

## Problem

The RPC client `hc` takes `init` options (passed on to `fetch` as its `RequestInit`) both when the
client is created and on each request; the two are merged, the request's values on top. When both set
`init.signal`, the request fails before it is sent:

```ts
import { hc } from 'hono/client'

const session = new AbortController()
const perRequest = new AbortController()

const client = hc('https://example.invalid', {
  init: { signal: session.signal },
  fetch: async (url, init) => {
    console.log(init.signal instanceof AbortSignal) // false today
    new Request(url, init) // TypeError today
    return new Response('ok')
  },
})

await client.test.$get(undefined, { init: { signal: perRequest.signal } })
```

Either signal alone works. With both, the `signal` that reaches `fetch` is a plain object, not an
`AbortSignal`, and `new Request(...)` or the runtime's `fetch` throws a `TypeError`. The same happens to
any other value in `init` that is an instance of a class, such as a Node `dispatcher` (an undici
`Agent`) set on the client and again on a request: what reaches `fetch` is a plain object copy, not the
instance.

## Why it matters

Setting a default signal (or agent) on the client and a narrower one on a single request is ordinary,
documented use of both options. It must not break the request.

## Scope

**In**
- How the client combines its own `init` with a request's `init`, in `src/client/`.
- Tests.

**Out**
- Combining two signals into one that aborts when either does; see Decisions.
- How headers are combined (the client's `headers` option has its own rules).
- The server side and the client's types.

## Decisions

- When both levels set the same key in `init` and the request's value is not a plain object (an
  `AbortSignal`, an agent, any class instance), the request's value is used as it is: the very same
  object reaches `fetch`. The two are not combined.
- A key set only on the client still reaches `fetch` as the very same object.
- Plain-object values and other keys keep merging as today: client `init: { credentials: 'include' }`
  with request `init: { mode: 'cors' }` gives `fetch` both.

## Done when

- [ ] In the example, `fetch` receives `perRequest.signal` itself, and `new Request(url, init)` does
      not throw.
- [ ] A class instance set on the client and on a request reaches `fetch` as the request's instance;
      on a request that does not set it, as the client's instance.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] `pnpm test` passes (after `pnpm run build`), and `pnpm run lint` and `pnpm run format` are clean.

## Notes for the implementer

- The client is in `src/client/` (`client.ts`, `utils.ts`), with tests beside it.
- Install with `pnpm install`, build with `pnpm run build` (the tests in `build/` need it), then run
  `pnpm test`. A single folder runs with `pnpm exec vp test --run src/client`.
- The Node adapter's "Should call onAbort" tests (`runtime-tests/node`) are timing-sensitive and can
  fail on a busy machine; that is known and not part of this ticket.
