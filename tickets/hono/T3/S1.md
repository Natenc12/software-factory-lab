# Bun WebSocket: an exception in a handler crashes the server and never reaches `onError`

## Problem

With the Bun adapter, an app defines its WebSocket handlers through `upgradeWebSocket`:

```ts
import { Hono } from 'hono'
import { upgradeWebSocket, websocket } from 'hono/bun'

const app = new Hono()
app.get(
  '/ws',
  upgradeWebSocket(() => ({
    onMessage(evt, ws) {
      JSON.parse(String(evt.data)) // throws on a bad message
    },
    onError(evt, ws) {
      console.error('ws error', evt)
    },
  }))
)

export default { fetch: app.fetch, websocket }
```

If `onOpen`, `onMessage` or `onClose` throws, the exception goes straight out of the adapter's
exported `websocket` handler (`open`, `message`, `close`). Under `Bun.serve` that is an uncaught
exception, and the whole server process exits with code 1 because one client sent a bad message.
The app's `onError` is never called: in the Bun adapter it is accepted but never used. An `async`
handler that rejects has the same problem: the rejection is unhandled and `onError` never hears of it.

## Why it matters

One misbehaving client must not take the server down, and an app that supplies `onError` expects it
to see the errors from its own handlers, as it does with the other runtimes' adapters.

## Scope

**In**
- The Bun adapter's `websocket` handler (`src/adapter/bun/websocket.ts`): errors thrown by
  `onOpen`, `onMessage` or `onClose`, and rejections of those handlers when they are `async`, go to the
  app's `onError`.
- The same handler in the separate `@hono/bun` package (`adapters/bun/src/websocket.ts`), kept in step.
- Tests.

**Out**
- Other adapters' WebSocket code, and `upgradeWebSocket`'s upgrade logic.
- What `open`, `message` and `close` do when no handler throws.

## Decisions

- `onError` is called with an `Event` whose `type` is `'error'` and whose `error` property is the
  thrown value (or the rejection reason), and with the same kind of `WSContext` the other handlers get
  for that socket (its `raw` is the Bun socket).
- The adapter's `open`, `message` and `close` deliver the error themselves, so calling them directly
  (as Bun does, and as the tests do) is enough to reach `onError`. One thrown error is one `onError`
  call.
- If the app set no `onError`, a thrown error still propagates out of `open`, `message` or `close`
  exactly as today; nothing is swallowed silently.

## Done when

- [ ] A handler that throws in `onOpen`, `onMessage` or `onClose` leads to one `onError` call each,
      with `evt.type === 'error'` and `evt.error` the thrown error.
- [ ] An `async` `onMessage` that rejects leads to one `onError` call with that error.
- [ ] Without `onError`, `websocket.message(ws, ...)` still throws the handler's error.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] `pnpm test` passes (after `pnpm run build`), and `pnpm run lint` and `pnpm run format` are clean.

## Notes for the implementer

- `src/adapter/bun/websocket.test.ts` drives `websocket.open`, `websocket.message` and `websocket.close`
  directly with a stand-in socket object; Bun itself is not needed. The `adapters/bun` package's own
  tests run with Bun (`bun test`) and are not part of `pnpm test`.
- Install with `pnpm install`, build with `pnpm run build` (the tests in `build/` need it), then run
  `pnpm test`. A single folder runs with `pnpm exec vp test --run src/adapter/bun`.
- The Node adapter's "Should call onAbort" tests (`runtime-tests/node`) are timing-sensitive and can
  fail on a busy machine; that is known and not part of this ticket.
