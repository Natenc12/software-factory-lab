# Adding an unrelated route can change the value of a repeated path parameter

## Problem

When a route repeats a parameter name, such as `/:id/:id/x`, the value `c.req.param('id')` returns
depends on which router ends up serving the app. With the default router (`SmartRouter`), adding a
route the request never reaches is enough to change it:

```ts
import { Hono } from 'hono'
import { getRouterName } from 'hono/dev'

const a = new Hono()
a.get('/:id/:id/x', (c) => c.text(c.req.param('id')))
await (await a.request('/123/456/x')).text() // '123'
getRouterName(a) // 'SmartRouter + RegExpRouter'

const b = new Hono()
b.get('/:id/:id/x', (c) => c.text(c.req.param('id')))
b.get('/a', (c) => c.text('a'))
await (await b.request('/123/456/x')).text() // '456'
getRouterName(b) // 'SmartRouter + TrieRouter'
```

The library already decided which value wins: when a name appears more than once in a path, the
**first** value is used. The shared router tests (`src/router/common.case.test.ts`, "Duplicate param
name > self") assert it for `/:id/:id` and `/123/456`, and `RegExpRouter`, `TrieRouter` and
`LinearRouter` all return `123` there. But:

- for `/:id/:id/x` and `/123/456/x`, `TrieRouter` returns `456` while `RegExpRouter` and
  `LinearRouter` return `123`;
- for `/:id/:id/:id` and `/1/2/3`, `TrieRouter` returns `2`, so it is not even taking the last value.

## Why it matters

The same route and the same request must give the same parameter value. Today an unrelated change to
an app's route list silently changes what a handler receives.

## Scope

**In**
- Making every router give the first value for a repeated parameter name, in every position: before
  a static segment, at the end, three or more times, and when one of the repeats has a pattern (for
  example `/:id/:id{[0-9]+}` matched against `/abc/123` gives `id` = `abc`).
- Tests.

**Out**
- Which router `SmartRouter` picks, and the order it tries them in.
- What a route with distinct parameter names returns.
- `PatternRouter`, which does not support repeated names (its tests already skip those cases).
- The separate packages under `adapters/`.

## Decisions

- The first value wins, as the existing "self" test already says. No router may return a later one.

## Done when

- [ ] Both apps in the example return `123`.
- [ ] `TrieRouter` returns `id` = `123` for `/:id/:id/x` and `/123/456/x`, and `id` = `1` for
      `/:id/:id/:id` and `/1/2/3`.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] `pnpm test` passes (after `pnpm run build`), and `pnpm run lint` and `pnpm run format` are clean.

## Notes for the implementer

- The routers are in `src/router/`; the cases every router must pass are in
  `src/router/common.case.test.ts`, which each router's `router.test.ts` runs, with a list of the
  cases that router skips.
- Install with `pnpm install`, build with `pnpm run build` (the tests in `build/` need it), then run
  `pnpm test`. A single folder runs with `pnpm exec vp test --run src/router`.
