# Show the request id in the logger's lines and the `Server-Timing` header

## Problem

`requestId()` gives each request an id (from the client's `X-Request-Id` header when acceptable,
otherwise generated) and stores it as the context variable `requestId`. Nothing else uses it: the
logger prints `<-- GET /path` and `--> GET /path 200 3ms` with no id, and the timing middleware's
`Server-Timing` header carries only durations. To match a slow response in a browser's network panel
with its log lines, an app has to write its own glue in every project.

## Why it matters

The id exists to tie one request's traces together. Having the built-in logger and timing middleware
pick it up makes every app that uses them traceable with no extra code.

## Scope

**In**
- `logger()` (`src/middleware/logger/`): put the request id on its lines.
- `timing()` (`src/middleware/timing/`): put the request id in the `Server-Timing` header.
- The JSDoc of the three middlewares where it describes their output; tests.

**Out**
- How `requestId()` accepts or generates an id, its options, and the response header it sets.
- New options for any of the three middlewares: the behaviour below is automatic.
- The separate packages under `adapters/`.

## Decisions

- **Which id.** The value of the context variable `requestId` (set by `requestId()`), if it is a
  non-empty string at the moment the logger prints a line or the timing middleware writes its header.
  Middleware order is the app's: neither middleware generates an id of its own.
- **Logger format.** The id goes in square brackets right after the arrow, on each line printed once
  the request has an id: `<-- [abc-123] GET /path` and `--> [abc-123] GET /path 200 3ms`. So with
  `app.use(logger())` registered before `app.use(requestId())`, the incoming line has no id and the
  outgoing line has it. A request without an id prints exactly the lines it prints today.
- **Server-Timing entry.** `reqid;desc="<id>"`, added as the last entry of the header the timing
  middleware writes (after the app's metrics and after `total`), whichever of the two middlewares is
  registered first. The description is quoted and escaped the same way as every other `desc` in that
  header (a `"` is sent as `\"`, a `\` as `\\`), because a custom id generator may return anything.
- When the timing middleware writes no header (`enabled: false`), nothing is added. Without an id, the
  header is exactly today's.

## Done when

- [ ] With `requestId({ generator: () => 'req-1' })` then `logger()`, a request to `/p?q=1` prints
      `<-- [req-1] GET /p?q=1` and a line starting `--> [req-1] GET /p?q=1 ` with the status and time.
- [ ] With `logger()` registered before `requestId()`, the first line has no id and the second has it.
- [ ] With `requestId({ generator: () => 'req-3' })` and `timing()`, a handler that calls
      `setMetric(c, 'db', 12.3, 'Database')` gets
      `db;dur=12.3;desc="Database",total;dur=…;desc="Total Response Time",reqid;desc="req-3"`, in
      either order of the two middlewares.
- [ ] An id `id "x"\` (from a custom generator) appears as `reqid;desc="id \"x\"\\"`.
- [ ] Tests for each case; every existing test passes unchanged.
- [ ] `pnpm test` passes (after `pnpm run build`), and `pnpm run lint` and `pnpm run format` are clean.

## Notes for the implementer

- The three middlewares are in `src/middleware/` (`request-id`, `logger`, `timing`), each with tests
  beside it. The logger colours the status code when colour is on; its existing tests show how.
- Install with `pnpm install`, build with `pnpm run build` (the tests in `build/` need it), then run
  `pnpm test`. A single folder runs with `pnpm exec vp test --run src/middleware`.
