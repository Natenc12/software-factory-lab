# Call a class a "course" in the API, step by step, without breaking any existing client

## Rules that hold for the whole change

Read these first. They are stated once, here, and every part below must respect them; most of them
matter most in the last parts.

1. **Old clients notice nothing.** Every request that works today gets exactly the same reply as
   today: the same status, the same body, the same error `kind` and the same message, word for word.
   That covers `POST /classes`, `POST /files` with `class_id`, and `POST /ask` with `class_id`,
   including their refusals (`bad_class_id`, `class_not_found`, and the `422` for a missing id, which
   still names `class_id`). The only addition an old client sees is the header in rule 6.
2. **A request that names the course as a course is answered in course words.** Where such a
   request is refused because of the id, the kind is `bad_course_id` or `course_not_found` and the
   message says "course" where today's says "class". That holds for `course_id` fields and for every
   `/courses` route.
3. **Two ids must agree.** A request that sends both `class_id` and `course_id` is accepted only if
   they name the same course (any spelling `uuid.UUID` accepts); then it is answered in course words.
   If they differ, or one of them is not a uuid, it is refused with `400` and kind `conflicting_ids`,
   before anything else happens: before the course is looked up and before any upload is staged.
4. **Nothing below the API changes name.** The database, the library (`gct.classes`, `gct.files`,
   the worker) and their tests keep saying "class". A course is a class. Below the API, add only
   what part 5 needs, in class words.
5. **Nothing is staged before the course is checked.** On every upload route, old or new, a request
   that is refused because of its course id leaves nothing in the staging folder.
6. **Old names are flagged on every reply.** Every reply to `POST /classes`, and every reply to
   `POST /files` or `POST /ask` whose request names the course only through `class_id`, carries the
   response header `Deprecation: true`: success or error, whatever the error, from the moment the
   route has read the id (a `422` that rejects the request body before that is exempt). A reply to a
   request that sends `course_id`, and every reply from a `/courses` route, never carries it.

## Problem

Students and teachers say "course", and the web client is about to follow, but the API only knows
"class": `POST /classes` creates one and returns `class_id`, and `POST /files` (form field) and
`POST /ask` (JSON body) take `class_id`. Renaming those outright would break every client already
in use.

## Why it matters

The new client should speak the product's language, and nobody using the old one should have to
change anything.

## The parts, in order

Build these in order; each part uses the ones before it.

1. **The id rules.** One place in `src/gct/api/` that decides, for a request, which course it names
   and in which words to answer it (rules 2 and 3).
2. **`POST /courses`.** Takes the same body as `POST /classes` (`{"name": ...}`), creates a class the
   same way, and answers `201` with `{"course_id": ..., "name": ...}`. Name refusals are the same kinds
   as for `POST /classes` (`blank_name`, `unstorable_name`).
3. **`course_id` on the old routes.** `POST /files` accepts the course as form field `course_id` or
   `class_id`; `POST /ask` accepts `course_id` or `class_id` in its JSON body. The rest of each request
   and every successful reply are unchanged. A request with neither id answers `422` `validation`, as
   a request without `class_id` does today.
4. **Deprecation.** `POST /classes` carries `deprecated: true` in the API schema, and every reply to
   an old-name request carries the header of rule 6.
5. **`GET /courses/{course_id}`.** Answers `200` with `{"course_id": <canonical id>, "name": ...,
   "files": {"queued": n, "processing": n, "ready": n, "failed": n}}`: how many of the course's files
   are in each status, with all four keys present (zero where there are none).
6. **Course-scoped routes.** `POST /courses/{course_id}/files` (multipart field `file` only) and
   `POST /courses/{course_id}/ask` (JSON body `{"question": ...}` only; any other key is a `422`) do
   what `POST /files` and `POST /ask` do, with the same success replies, for the course in the path.

Every `/courses` route accepts every spelling of the id that `uuid.UUID` accepts, answers a malformed
id with `400` `bad_course_id`, and a course this owner does not have with `404` `course_not_found` (a
missing course and another owner's course look the same, as today).

Also regenerate the committed API snapshot `web/openapi.json`
(`uv run python web/scripts/openapi_snapshot.py`); update `design/components/api.md` if you like; add
tests for every part.

## Out of scope

- The web client under `web/src/`, including `web/src/api/schema.gen.ts`: do not regenerate it.
- Database columns and migrations; renaming anything below `src/gct/api/`.
- Removing or renaming anything old clients use.
- `GET /files/{file_id}` and every reply body that does not carry a class id today.

## Done when

- [ ] Every part works as described, and a course created with `POST /courses` works as `class_id`
      everywhere (and an id from `POST /classes` as `course_id`).
- [ ] Requests in course words are answered in course words; requests with `class_id` only are
      answered exactly as today, plus the `Deprecation` header.
- [ ] Two disagreeing ids are refused with `conflicting_ids` before anything is staged, and no upload
      route stages anything for a refused course id.
- [ ] Tests for every part; every existing test passes unchanged; `uv run ruff check` and
      `uv run ruff format --check .` are clean.

## Notes for the implementer

- The routes are in `src/gct/api/routers/` (`classes.py`, `files.py`, `ask.py`) and are mounted in
  `src/gct/api/app.py`. `tests/gct/api/conftest.py` has the `api` fixture.
- Tests run with `uv run pytest -m "not live"` against `DATABASE_URL`, after
  `uv run python scripts/migrate.py`.
