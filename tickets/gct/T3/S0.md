# id spelling trap still open outside enqueue

We fixed `enqueue` so a class id spelled in a way Python accepts but Postgres doesn't (like
`urn:uuid:...`) gets normalised before it hits the `::uuid` cast. The same trap is still in other
library functions:

- `retrieve` and `index_file` pass `class_id` raw into the SQL. `retrieve` can leave the connection in
  an aborted transaction; `index_file` is reached after embeddings are already paid for.
- `class_exists` and `get_file_status` only catch `ValueError`, so `None` or a `uuid.UUID` object blows
  up with a `TypeError`/`AttributeError` from the parser.

Make every id a caller can pass either normalised or refused with a clear `ValueError`, like `enqueue`
does. Add tests both ways.
