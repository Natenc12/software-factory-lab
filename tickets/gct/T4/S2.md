# Let a student delete a file they uploaded

## Problem

There is no way to remove an uploaded file. A student who uploads the wrong lecture, or an old
version, keeps getting answers cited from it, because its chunks stay in the class for good. The
API has `POST /files` and `GET /files/{file_id}` (`src/gct/api/routers/files.py`), and the library
has `get_file_status` (`src/gct/files.py`), but nothing deletes.

An upload touches four places: the staged bytes on disk (written by `stage` in `src/gct/staging.py`,
at the path stored as `files.staging_ref`), the `files` row, the `jobs` row the worker claims
(`src/gct/jobs/`), and, once processed, the file's `chunks`.

## Why it matters

Students need to fix their own mistakes, and an answer must never cite a file the student removed.

## Scope

**In**
- A library function `delete_file(conn, *, file_id, owner_id) -> bool` in `src/gct/files.py`, and an
  exception `FileBusy` in the same module.
- Removing the staged bytes (a helper in `src/gct/staging.py` is the natural home).
- A route `DELETE /files/{file_id}` in `src/gct/api/routers/files.py`, and the committed API
  snapshot `web/openapi.json`, which a test compares with the live schema (regenerate it with
  `uv run python web/scripts/openapi_snapshot.py`).
- Tests.

**Out**
- Deleting classes, or deleting several files at once.
- Any change to the worker, the queue's claim logic or retrieval.
- Soft delete, undo, or keeping deleted rows around.
- The web client's code under `web/src/`, including `web/src/api/schema.gen.ts`: do not regenerate
  it, even though the snapshot test's message suggests it; that is a follow-up. Also the schema (no
  migration is needed; the existing migration files stay byte-identical).

## Decisions

- `delete_file` removes the file's `chunks`, its `jobs` row and its `files` row, all or nothing, and
  then removes the staged bytes. It returns `True` when it deleted the file.
- It returns `False`, and changes nothing, when there is no such file for this owner. A file that
  does not exist and another owner's file look the same, exactly as `get_file_status` treats them.
- It accepts the same `file_id` spellings `get_file_status` accepts, and refuses a malformed id with
  `ValueError` the same way.
- **A file the worker is on cannot be deleted.** That is the case when the `files` row is
  `processing`, and also when its job is already `processing` (the worker marks the job first and the
  file a moment later). `delete_file` then raises `FileBusy` and changes nothing.
- A file that is `queued`, `ready` or `failed` can be deleted. A deleted queued file is never
  processed afterwards.
- Staged bytes that are already gone do not stop a delete.
- The route answers `204` with no body on success, `404` with kind `file_not_found` when
  `delete_file` returns `False`, `400` with kind `bad_file_id` for a malformed id, and `409` with kind
  `file_busy` for `FileBusy`. Errors use the existing error envelope.

## Done when

- [ ] Deleting a ready file removes its rows and its staged bytes; other files in the class, their
      rows and their bytes are untouched; `retrieve` no longer returns its chunks.
- [ ] Another owner's file and an unknown id both give `False` / 404 and change nothing.
- [ ] A file the worker is on gives `FileBusy` / 409 and changes nothing.
- [ ] A deleted queued file is never picked up by the worker.
- [ ] Tests cover the library function and the route; every existing test passes; `uv run ruff check`
      and `uv run ruff format --check .` are clean.

## Worked examples

Class C (owner O) holds `week-1.pdf` and `week-2.pdf`, both `ready`, each with chunks, a `done` job
and staged bytes.

| # | Call | Result |
|---|---|---|
| 1 | `delete_file(conn, file_id=<week-1>, owner_id=O)` | `True`. No `files`, `jobs` or `chunks` rows remain for week-1 and its staged file is gone. week-2's rows and bytes are untouched. `retrieve` over C returns only week-2 chunks. `get_file_status` for week-1 returns `None` |
| 2 | `delete_file(conn, file_id=<week-2>, owner_id="someone-else")` | `False`; nothing changes |
| 3 | `delete_file(conn, file_id=<a random uuid>, owner_id=O)` | `False` |
| 4 | `delete_file(conn, file_id="not-a-file-id", owner_id=O)` | `ValueError` |
| 5 | `DELETE /files/<week-2>` as O | `204`, empty body; then `GET /files/<week-2>` is 404 |
| 6 | `DELETE /files/<week-2>` again | `404`, kind `file_not_found` |
| 7 | `DELETE /files/not-a-uuid` | `400`, kind `bad_file_id` |
| 8 | A file whose `files.status` is `processing`: `DELETE /files/<it>` | `409`, kind `file_busy`; nothing changes |

## Failure cases that must hold

- A queued file whose job is already `processing` (claimed, but the file row not yet moved):
  `delete_file` raises `FileBusy`; its rows and bytes stay.
- A `queued` file that is deleted is never processed: the next `process_one` finds no job.
- A file whose staged bytes were already removed is still deleted (`True`).
- `delete_file` accepts a `urn:uuid:` spelling of the id, like `get_file_status`.

## Must not change

- `POST /files`, `GET /files/{file_id}` and `get_file_status`.
- The worker (`src/gct/jobs/worker.py`), the queue's claim logic and `retrieve`.
- Every file in `migrations/`.
- Existing tests: do not delete them or weaken their assertions.
