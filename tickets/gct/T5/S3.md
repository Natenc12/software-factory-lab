# Stop one owner from creating two classes with the same name

## Problem

`create_class` (`src/gct/classes.py`) and `POST /classes` (`src/gct/api/routers/classes.py`) accept
any non-blank name, so a student who taps "create" twice, or forgets they already made the class,
ends up with two classes called the same thing. Their uploads then split across the two, and
answers in one class miss the notes uploaded to the other.

## Why it matters

A class is how a student scopes their notes. Two classes with one name look identical in every list
and silently divide the material.

## Scope

**In**
- `create_class` and `POST /classes`.
- Tests.

**Out**
- Renaming, merging or listing classes.
- Classes that already share a name: leave them exactly as they are. The rule applies when a class
  is created.
- `ClassNameError` and its closed set of reasons (`CLASS_NAME_REASONS`); existing tests pin that set
  and the router's map of it.
- The web client, and the applied migration files (`migrations/0001_init.sql`,
  `migrations/0003_failed_reason_too_long.sql`, `migrations/0004_one_worker.sql`).

## Decisions

- `create_class` refuses a name the same owner already uses by raising a new exception,
  `ClassNameTaken`, defined in `src/gct/classes.py` (a subclass of `ValueError`). Nothing is
  written.
- `POST /classes` answers that with `409`, kind `class_name_taken`, and a short message, in the
  existing error envelope. Blank and unstorable names keep their existing `400` replies.
- Different owners may use the same name.
- Names are still stored exactly as typed; the check does not change what is saved.
- Deploying this must not fail on a database where an owner already has two classes with the same
  name, and those classes stay as they are.
- **Two names are the same** when they match after trimming whitespace at both ends, collapsing
  every run of whitespace inside (spaces, tabs, newlines) to a single space, and ignoring letter
  case. Everything else counts: punctuation, digits and accents. So `"Biology 101"`,
  `"biology 101"`, `"  BIOLOGY   101 "` and `"Biology\t101"` are one name, while `"Biology-101"`,
  `"Biology 102"` and `"Biologie 101"` are three others.

## Done when

- [ ] Creating a class with a name the owner already uses raises `ClassNameTaken` /
      answers 409 `class_name_taken`, and writes nothing.
- [ ] Another owner can still use that name.
- [ ] Existing duplicate classes are untouched, and `scripts/migrate.py` still runs cleanly on a
      database that has some.
- [ ] Tests for the above; every existing test passes; `uv run ruff check` and
      `uv run ruff format --check .` are clean.

## Worked examples

Owner O already has a class named `Biology 101`.

| # | Call | Result |
|---|---|---|
| 1 | `create_class(conn, owner_id=O, name="Biology 101")` | `ClassNameTaken`; no row written |
| 2 | `create_class(conn, owner_id=O, name="biology 101")` (also `"BIOLOGY 101"`) | `ClassNameTaken` |
| 3 | `create_class(conn, owner_id=O, name="  Biology   101 ")` (also `"Biology\t101"`) | `ClassNameTaken` |
| 4 | `create_class(conn, owner_id=O, name="Biology-101")` (also `"Biology 102"`, `"Biologie 101"`) | A new class, stored with exactly that name |
| 5 | `create_class(conn, owner_id=P, name="biology 101")` for another owner P | A new class for P |
| 6 | `POST /classes {"name": "biology 101"}` as O | `409`, `error.kind == "class_name_taken"` |
| 7 | `POST /classes {"name": "Chemistry"}` as O | `201` with the new `class_id` and `name` |

## Failure cases that must hold

- A name with extra spaces, such as `"  Chemistry   One "`, is stored exactly like that, and a later
  `"chemistry one"` for the same owner is refused.
- If O already has two classes `Algebra` and `algebra ` from before this change, running
  `scripts/migrate.py` succeeds, both classes stay, and creating `ALGEBRA` is refused.
- `POST /classes {"name": "   "}` still answers `400` `blank_name`.

## Must not change

- `ClassNameError`, `CLASS_NAME_REASONS` and the router's `_NAME_REFUSAL` map, and their `400`
  replies.
- The `201` reply for a new class.
- Existing classes, and the applied migration files.
- Existing tests: do not delete them or weaken their assertions.

## Acceptance tests

`tests/acceptance/test_class_names_are_unique.py` is already in the branch. It encodes worked
examples 1, 2, 5 and 6 and must pass. It does not cover everything above: the rest of this ticket
still applies.
