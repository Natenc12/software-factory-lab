# Stop one owner from creating two classes with the same name

## Problem

`create_class` (`src/gct/classes.py`) and `POST /classes` (`src/gct/api/routers/classes.py`) accept
any non-blank name, so a student who taps "create" twice, or forgets they already made the class,
ends up with two classes called the same thing. Their uploads then split across the two, and
answers in one class miss the notes uploaded to the other.

## Why it matters

A class is how a student scopes their notes. Two classes with one name look identical in every list
and silently divide the material.

## Scope

**In**
- `create_class` and `POST /classes`.
- Tests.

**Out**
- Renaming, merging or listing classes.
- Classes that already share a name: leave them exactly as they are. The rule applies when a class
  is created.
- `ClassNameError` and its closed set of reasons (`CLASS_NAME_REASONS`); existing tests pin that set
  and the router's map of it.
- The web client, and the applied migration files (`migrations/0001_init.sql`,
  `migrations/0003_failed_reason_too_long.sql`, `migrations/0004_one_worker.sql`).

## Decisions

- `create_class` refuses a name the same owner already uses by raising a new exception,
  `ClassNameTaken`, defined in `src/gct/classes.py` (a subclass of `ValueError`). Nothing is
  written.
- `POST /classes` answers that with `409`, kind `class_name_taken`, and a short message, in the
  existing error envelope. Blank and unstorable names keep their existing `400` replies.
- Different owners may use the same name.
- Names are still stored exactly as typed; the check does not change what is saved.
- Deploying this must not fail on a database where an owner already has two classes with the same
  name, and those classes stay as they are.
- **Not yet decided:** exactly when two names count as "the same" name.

## Done when

- [ ] Creating a class with a name the owner already uses raises `ClassNameTaken` /
      answers 409 `class_name_taken`, and writes nothing.
- [ ] Another owner can still use that name.
- [ ] Existing duplicate classes are untouched, and `scripts/migrate.py` still runs cleanly on a
      database that has some.
- [ ] Tests for the above; every existing test passes; `uv run ruff check` and
      `uv run ruff format --check .` are clean.

## Notes for the implementer

- `tests/gct/test_classes.py` and `tests/gct/api/test_classes_router.py` show how classes are tested;
  the `api` fixture in `tests/gct/api/conftest.py` builds the real app for a test owner.
- Tests run with `uv run pytest -m "not live"` against `DATABASE_URL`, after
  `uv run python scripts/migrate.py`.
