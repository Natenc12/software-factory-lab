# A request that fails validation can crash the error reply or get echoed back whole

## Problem

When a request fails validation, the API answers 422 with the error envelope from
`src/gct/api/errors.py`: `{"error": {"kind": "validation", "message": ..., "detail": [...]}}`, where
`detail` is pydantic's per-field list and each entry carries the client's rejected value under
`input`. Because that value is the client's own, two things go wrong. Both reproduce today with a
`TestClient` over `create_app()`:

1. **One byte turns the reply into a 500.** `POST /classes` with the one-byte body `b"\xff"` and no
   content type (or `application/octet-stream`, `text/plain`, `multipart/form-data`) returns
   `500 {"error": {"kind": "internal", ...}}`. The body reaches validation as raw bytes, and turning
   the error list into JSON fails on bytes that are not UTF-8. The client is blamed with a server
   error for its own malformed request, and the field list it needed is lost.
2. **The reply is as large as the request.** A body labelled `multipart/form-data` sent to a JSON route
   is not covered by the 64 KiB request-body bound in `src/gct/api/limits.py` (multipart is exempt on
   purpose, so uploads get through). It is rejected with a 422 whose `detail` carries the whole body
   back: 2,000,000 bytes in, 2,000,215 bytes out.

## Why it matters

Any client, with no credentials, can make the server report its own fault for a client mistake, or
make it send back a reply as big as whatever it sent. Error replies should stay correct and small no
matter what the client put in the request.

## Scope

**In**
- How error replies render what they echo from the request (`src/gct/api/errors.py`, and any setting
  you add in `src/gct/config.py`).
- The envelope section of `design/components/api.md`, if it needs to describe the new behaviour.
- Tests.

**Out**
- The request-body bound in `src/gct/api/limits.py`, including its multipart exemption, its 413
  `body_too_large` and 400 `body_too_nested` replies. Do not change what requests are accepted.
- The upload size limit for `POST /files`.
- Status codes and `kind` values of any reply; the shape of a successful reply; the web client.
- Applied migrations under `migrations/`.

## Decisions

- These requests get a 422 `validation` reply with the per-field list, never a 500.
- Every 422 entry keeps its keys (`type`, `loc`, `msg`, `input`); nothing is dropped from the shape.
- Bytes that are not valid UTF-8 are shown as text, with each undecodable byte replaced by U+FFFD (the
  Unicode replacement character). The one-byte body `b"\xff"` is echoed as `"�"`.
- **Echo bound: 512 characters.** Any string an error reply echoes from the request, wherever it
  appears in the reply (the rejected `input`, a client-supplied field name inside `loc`, or anywhere
  else), is at most 512 characters. A string of 512 characters or fewer comes back exactly as sent.
  A longer one keeps its beginning, and the returned string, including any marker, is at most 512
  characters and states the original length in characters (for example, ending in
  `...[truncated from 2000000 chars]`).
- An ordinary rejected value (a small object or a short string) is still echoed back whole, exactly
  as today.

## Done when

- [ ] `POST /classes` with `b"\xff"` and no content type returns 422 `validation`, and the first
      `detail` entry has `loc == ["body"]`.
- [ ] `POST /classes` with 2,000,000 bytes labelled `multipart/form-data` returns a 422 whose whole
      response is under 4 KB.
- [ ] No string an error reply echoes is longer than 512 characters, and strings up to 512 come back
      unchanged.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] Every existing test passes; `uv run ruff check` and `uv run ruff format --check .` are clean.

## Worked examples

| # | Request | Expected reply |
|---|---|---|
| 1 | `POST /classes`, body `b"\xff"`, no content type | 422; `error.kind == "validation"`; `detail[0].loc == ["body"]`; `detail[0].input == "\ufffd"` |
| 2 | As 1, with content type `application/octet-stream`, `text/plain` or `multipart/form-data` | Same as 1 |
| 3 | `POST /classes`, body of 2,000,000 `x` bytes, content type `multipart/form-data` | 422; the whole response is under 4 KB; `detail[0].loc == ["body"]`; `detail[0].input` starts with `xxxx`, is at most 512 characters and mentions `2000000` |
| 4 | `POST /classes`, JSON `{"nome": "Philosophy 101"}` | 422; `detail[0].loc == ["body", "name"]`; `detail[0].input == {"nome": "Philosophy 101"}` (unchanged from today) |
| 5 | A JSON field that must be an integer, sent a string of exactly 512 characters | 422; that entry's `input` is the same 512-character string |
| 6 | As 5, with a string of 513 characters | 422; that entry's `input` is at most 512 characters, starts with the string's first characters and mentions `513` |

## Failure cases that must hold

- On a route whose model forbids unknown keys, a request with a 5,000-character unknown key gets a 422
  where every part of every `loc` is at most 512 characters, and the whole reply is under 4 KB.
- A JSON body just under the 64 KiB request bound, holding one long string that fails validation, gets
  a 422 under 4 KB.
- A non-finite number (`NaN`) and a lone surrogate in a rejected value still render as they do today
  (no 500).
- A raising field validator still produces a 422 whose entry carries the validator's message.

## Must not change

- The envelope shape `{"error": {"kind", "message", "detail"}}`, every `kind` value and every status
  code.
- `src/gct/api/limits.py`: the request-body bound, the multipart exemption, and its 413 and 400 replies.
- Behaviour of every route for valid requests.
- Every file in `migrations/`.
- Existing tests: do not delete them or weaken their assertions.
