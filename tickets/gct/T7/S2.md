# Store chunk page numbers as integers, keeping every existing row

## Problem

`chunks.page_or_slide` was created as `text` in `migrations/0001_init.sql`, but everything in
`src/gct` treats a page or slide number as an `int`: the parser produces 1-based ints, `index_file`
(`src/gct/ingest/index.py`) converts each one to a string on the way in, and `retrieve`
(`src/gct/retriever/retrieve.py`) converts it back with `int(...)` on the way out. As text the column
sorts page 10 before page 2 (tests have to write `order by page_or_slide::int`), and it accepts values
no page can have, such as `'0'`, `''` or `'iv'`.

## Why it matters

A citation's page number is the product's honesty guarantee. The database should hold it as a number
and refuse impossible ones, instead of every reader and writer converting by hand.

## Scope

**In**
- A new migration that changes `chunks.page_or_slide` to `integer` on databases that already hold
  chunks.
- `index_file` and `retrieve` (and any docstring or comment that describes the text column).
- Tests. Existing tests that assert the column holds text may be updated to the new type; nothing
  else in them should change.

**Out**
- Any other column or table, the API, and the citation format the grounder renders.
- `scripts/migrate.py`.
- The migration files that are already applied: `migrations/0001_init.sql`,
  `migrations/0003_failed_reason_too_long.sql` and `migrations/0004_one_worker.sql` must stay
  byte-for-byte as they are. Existing databases have run them; editing them changes nothing there.

## Decisions

- The change goes in a new file in `migrations/`, numbered after the existing ones.
- After it runs, `chunks.page_or_slide` is an `integer` column and every existing row holds the same
  number it held as text (`'10'` becomes `10`). No row is added, removed or otherwise changed.
- The database refuses a page or slide number below 1 from then on.
- If any existing value is not a whole number of at least 1, the migration must fail with an error
  and leave the database exactly as it was. Do not delete, null out, or guess a value for such a row;
  a person will look at it and fix it, and the next run then succeeds.
- `scripts/migrate.py` applies every file in `migrations/` on every run, in one transaction. The new
  migration must therefore be safe to run again and again: on an already converted database it
  changes nothing, and on a brand new empty database the full set still ends with an integer column.
- `index_file` writes the number as an integer and `retrieve` returns it as an `int`, as today.

## Done when

- [ ] On a database that already holds chunks with page values `'1'`, `'2'`, `'10'`, running the
      migrations (twice) leaves an integer column holding 1, 2 and 10, ordered numerically.
- [ ] A value that is not a whole number of at least 1 makes the migration fail and changes nothing.
- [ ] Inserting a chunk with page 0 fails.
- [ ] The three applied migration files are unchanged.
- [ ] Tests for the above are added; every existing test passes (updated only where it asserted the
      text type); `uv run ruff check` and `uv run ruff format --check .` are clean.

## Worked examples

| # | Starting state | Action | After |
|---|---|---|---|
| 1 | A database at the current schema with chunks whose `page_or_slide` is `'1'`, `'2'`, `'10'`, `'3'` | `scripts/migrate.py` | Column type `integer`; each chunk holds 1, 2, 10, 3 respectively; `order by page_or_slide` gives 1, 2, 3, 10; same number of chunks, same text |
| 2 | The database after example 1 | `scripts/migrate.py` again | Nothing changes; it exits 0 |
| 3 | A brand new empty database | `scripts/migrate.py`, twice | Exits 0 both times; `page_or_slide` is `integer` |
| 4 | Migrated database | `index_file` with chunks on pages 2, 10 and 1 | Stored as integers 2, 10, 1; `retrieve` returns those chunks with `page_or_slide` as `int` |
| 5 | Migrated database | Insert a chunk with `page_or_slide = 0` (or `-3`) | The insert fails with an integrity error |

## Failure cases that must hold

- Existing rows `'1'`, `'iv'`, `'7'`: `scripts/migrate.py` exits non-zero; the column is still `text`
  and the three rows still hold `'1'`, `'iv'`, `'7'`.
- Same, with `'0'` in place of `'iv'`: it still fails and changes nothing.
- After a person changes that row to `'4'`, `scripts/migrate.py` succeeds and the rows hold 1, 4, 7.

## Must not change

- `migrations/0001_init.sql`, `migrations/0003_failed_reason_too_long.sql`,
  `migrations/0004_one_worker.sql` (byte-identical) and `scripts/migrate.py`.
- Every other column of `chunks`, and every other table.
- `RetrievedChunk` and `PreparedChunk`: field names and types.
- The API's citation output.
- Existing tests, except assertions that the column holds text.

## Notes for the implementer

- Run migrations with `uv run python scripts/migrate.py` (the app's CI runs it twice on a fresh
  database). Tests run with `uv run pytest -m "not live"` against `DATABASE_URL`.
- To test against existing data you need a database at the old schema with rows in it before your
  migration runs; the test database the suite uses has already been migrated.
