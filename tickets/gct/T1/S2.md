# A file's status row can describe an attempt or an owner that is no longer true

## Problem

Each uploaded file has one row in `files` (status, `failed_reason`, `filename`, `owner_id`,
`class_id`) and a set of rows in `chunks`. Two paths leave the `files` row saying something false.

1. **A stale failure reason survives a retry.** When the worker gives up on a file it writes
   `files.status = 'failed'` with a `failed_reason`, and then settles the job in `jobs`. The two
   writes are separate, so the job half can fail to settle (a crash between them, or the job's lease
   having already expired). The job then stays claimable and the worker picks the file up again. The
   row moves back to `processing`, but it still carries the earlier attempt's `failed_reason` for the
   whole of the new attempt. If the new attempt succeeds (for example because the bytes at the file's
   staging path changed), the file is published `ready` with that old reason still attached.
2. **A re-index keeps the old scope.** `index_file` (`src/gct/ingest/index.py`) replaces a file's
   chunks wholesale from the arguments of the current call, but when the `files` row already exists
   it only updates `status` and `updated_at`. Re-indexing the same `file_id` under a different
   `filename`, `owner_id` or `class_id` leaves the `files` row describing the old values while every
   chunk carries the new ones.

## Why it matters

`failed_reason` is the message a student is shown about their upload. A file that is being worked on,
or is already `ready`, must not tell them it failed. Retrieval filters chunks by owner and class and
cites `chunks.file`, so a `files` row that disagrees with its own chunks means a status read and an
answer describe different files, and nothing in the data shows which one is right.

## Scope

**In**
- The worker's handling of a file it picks up again (`src/gct/jobs/worker.py`).
- The `files` upsert in `index_file` (`src/gct/ingest/index.py`).
- Tests that would have caught both.

**Out**
- The out-of-order case where a worker whose lease has already expired writes a failure *after* a
  newer attempt has started. That is tracked separately; leave it alone.
- The retry budget, backoff, lease length and reaper behaviour.
- The schema: no new migration, and the existing files in `migrations/` stay byte-identical.
- The API, the CLI scripts and anything under `design/`.

## Decisions

- A re-index makes the `files` row match the call: `filename`, `owner_id` and `class_id` come from
  the incoming call, the same values the new chunks carry. `status` is still set to `ready` by
  `index_file` itself.
- From the moment the worker picks a file up for a new attempt, its `files` row must not show any
  earlier attempt's `failed_reason`. If that attempt fails terminally, the row shows the new reason;
  if it fails transiently, the row stays `processing` with no reason; if it succeeds, the row is
  `ready` with no reason.
- A `files` row that is already `ready` is not changed by the worker picking up its job: not its
  status and not its `failed_reason`.
- Only the student-facing column is about "now". The job's own error history (`jobs.last_error`)
  is kept as it is.
- A re-index that is refused (for example because the new `class_id` has no `classes` row) changes
  nothing: the old `files` row and the old chunks stay exactly as they were.

## Done when

- [ ] Re-indexing an existing `file_id` with a new filename, owner or class leaves the `files` row and
      all of its chunks agreeing on all three.
- [ ] A file whose previous attempt left `('failed', <reason>)` reads `('processing', NULL)` as soon as
      the worker picks it up again, and ends `('ready', NULL)`, `('failed', <new reason>)` or
      `('processing', NULL)` depending on how that attempt ends.
- [ ] A `ready` row is untouched by a pick-up of its job.
- [ ] Tests that fail on today's code and pass with the fix are added.
- [ ] Every existing test passes; `uv run ruff check` and `uv run ruff format --check .` are clean.

## Worked examples

Every "after" is read through a second connection, so it describes committed rows only.

| # | Starting state | Action | After |
|---|---|---|---|
| 1 | `files` row `ready`, `old.pdf`, owner A, class X; its chunks carry `old.pdf` / A / X | `index_file` for the same `file_id` with `new.pdf`, owner B, class Y and chunks carrying `new.pdf` / B / Y | `files`: `ready`, `new.pdf`, B, Y. Every chunk: `new.pdf`, B, Y |
| 2 | As 1 | `index_file` for the same `file_id`, only the filename changed to `renamed.pdf` | `files.filename` is `renamed.pdf`; owner and class unchanged |
| 3 | The previous attempt was interrupted after writing `('failed', 'unparseable')`; the job is still `queued` | The worker picks the job up; the provider answers the embed with a 429 once | `files` is `('processing', NULL)`; the job is `queued` again with `attempts = 2` |
| 4 | As 3, and the staging path now holds a valid PDF | The worker picks the job up | `files` is `('ready', NULL)`; the job is `done`; the file has chunks; `jobs.last_error` still holds the first attempt's error |
| 5 | As 3 | The worker picks the job up and the attempt fails terminally with reason `empty` | While the attempt runs, `files` is `('processing', NULL)`; afterwards `('failed', 'empty')` |

## Failure cases that must hold

- A row set by hand to `('ready', 'unparseable')` whose job is picked up by the worker stays
  `('ready', 'unparseable')`.
- Re-indexing an existing file into a `class_id` that has no `classes` row raises, and afterwards the
  `files` row (filename, owner, class, status) and the old chunks are exactly as before.
- `index_file` with an empty chunk list still raises `ValueError` and writes nothing, as today.

## Must not change

- The signatures of `index_file`, `process_one`, `enqueue` and the worker's other public functions.
- The set of allowed `failed_reason` values, and every file in `migrations/`.
- `jobs.last_error`: what it records and when.
- A terminal failure still cannot move a `ready` file back to `failed`.
- Retry budget, backoff and lease behaviour.
- Existing tests: do not delete them or weaken their assertions. Adding tests, or extending a test
  helper, is fine.

## Notes for the implementer

- The interrupted-failure state is easy to reach in a test: interrupt the worker's terminal-failure
  path after its `files` write and before its `jobs` write. `tests/gct/jobs/test_worker.py` already
  has a test that does this (`test_an_interrupt_inside_bury_self_heals_on_the_next_attempt`).
- Read what was published through a second connection (the `db_other` fixture in
  `tests/conftest.py`), not through the connection that wrote it.
- Tests run with `uv run pytest -m "not live"` against the Postgres in `DATABASE_URL`, after
  `uv run python scripts/migrate.py`.
