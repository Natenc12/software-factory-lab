# Let a student replace an uploaded file, keep its versions, and restore an earlier one

## Rules that hold for the whole change

Read these first. They are stated once, here, and every part below must respect them; most of them
only bite in the later parts.

1. **A ready file keeps answering until a new version is published.** While a new version is on its
   way (a replacement or a restore), the file's status stays `ready` (never `queued` or
   `processing`) and questions are answered from its current chunks.
2. **A failed new version changes nothing.** If it fails for any reason (a terminal parse failure, or
   the retry budget running out), the file keeps its current content, chunks, filename and status,
   and `GET /files/{file_id}` says the replacement failed and why.
3. **Nothing staged is deleted.** Staged uploads are kept on purpose (ADR 0010), and part 5 depends
   on it: an old version can only be restored if its bytes are still on disk. The file's
   `staging_ref` always points at the bytes its published chunks came from, so it moves only when a
   new version is published.
4. **A refused request stages nothing.** Every refusal is decided before any bytes are written to the
   staging folder.
5. **The filename changes only on publish.** Until then the file keeps its current name.
6. **Every upload is a numbered version.** The first upload of a file is version 1 and each later
   version (replacement or restore) takes the next number: 1, 2, 3, never reused and with no gaps, so
   a failed version keeps its number. Each version ends `published` or `failed` (with its reason), or
   is `pending` until the worker settles it.
7. **Files that already exist are version 1.** The database already holds files when this ships.
   Each of them must show up as version 1, with an outcome that matches its status: `ready` is
   `published`, `failed` is `failed` with its `failed_reason`, `queued` or `processing` is `pending`.

## Problem

A student who uploads the wrong version of a lecture, or an updated one, can only upload it again as
a second file, so the class ends up with both versions and answers cite the stale one. There is no
way to give an existing file new contents, to see what was uploaded before, or to go back.

## Why it matters

Students revise their notes during a term. Replacing a file in place keeps the class clean and keeps
every reference to the file's id valid; a history and a restore make a bad replacement harmless.

## The parts, in order

Build these in order; each part needs the one before it.

1. **Storage.** A new migration for what replacements and versions need, which also brings every
   existing file into the version history (rule 7). The applied migration files (`0001_init.sql`,
   `0003_failed_reason_too_long.sql`, `0004_one_worker.sql`) stay byte-identical, and
   `scripts/migrate.py` re-applies every migration on every run, so yours must be safe to re-run.
2. **Library.** In `src/gct/files.py` and `src/gct/jobs/`: queueing a replacement for an existing
   file, recording each version, and reading a file's versions.
3. **Worker.** In `src/gct/jobs/worker.py`: processing a new version under rules 1, 2, 3, 5 and 6, and
   settling its version as `published` or `failed`.
4. **API.** `PUT /files/{file_id}`, the two new keys on `GET /files/{file_id}`, and
   `GET /files/{file_id}/versions`, all below.
5. **Restore.** `POST /files/{file_id}/versions/{version}/restore`, below. It brings an earlier
   version back by queueing its kept bytes as the next version, so it works only if parts 1 to 4
   kept every version's bytes and record.

Also regenerate the committed API snapshot `web/openapi.json`
(`uv run python web/scripts/openapi_snapshot.py`), and add tests for every part. An existing test that
asserts the exact `GET /files/{file_id}` body may be updated for the two new keys; change nothing
else in it.

## Out of scope

- The web client under `web/src/`, including `web/src/api/schema.gen.ts`: do not regenerate it.
- `POST /files` and how a first upload is processed, apart from recording it as version 1.
- Deleting files or versions.
- Retrieval, the grounder and the answer path.

## Decisions

- **Which files can take a new version:** a `ready` file or a `failed` file. A `queued` or
  `processing` file, or a `ready` file whose new version is still pending, answers `409` with kind
  `file_busy`.
- **Owner scoping:** on every route here, a missing file and another owner's file both answer `404`
  with kind `file_not_found`, the same reply `GET /files/{file_id}` gives for a missing file, and a
  malformed id answers `400` with kind `bad_file_id`.
- **`PUT /files/{file_id}`** takes the new file as a multipart field named `file`, like `POST /files`,
  and answers an accepted replacement with `202` and the same body as `POST /files`: `file_id` and the
  new upload's `filename`. Staging refusals (`bad_filename`, `too_large`) are the same as for
  `POST /files`.
- **A `failed` file** that gets a new version is processed like a new upload: it goes back to
  `queued` with no `failed_reason`, then `processing`, then `ready` or `failed`.
- **`GET /files/{file_id}`** always carries two more keys:
  - `replacement`: `"pending"` while a `ready` file's new version waits to be published, `"failed"`
    when its most recent new version failed, otherwise `null`;
  - `replacement_failed_reason`: when `replacement` is `"failed"`, the reason (one of the
    `failed_reason` values), otherwise `null`.
- A new version clears the record of an earlier failed one. A transient provider error is retried as
  for any upload; while it is retried the version stays pending.
- **`GET /files/{file_id}/versions`** answers `200` with `{"versions": [...]}`, newest version first.
  Each entry has exactly `version` (the number), `filename` (that upload's name), `outcome`
  (`"pending"`, `"published"` or `"failed"`), `failed_reason` (the reason for a failed version,
  otherwise `null`) and `current` (`true` only for the version whose content the file serves now:
  the highest-numbered published one; a file with no published version has none).
- **`POST /files/{file_id}/versions/{version}/restore`** queues that version's kept bytes as the
  file's next version, under the same rules as a replacement, and answers `202` with
  `{"file_id": ..., "filename": <that version's filename>, "version": <the new version's number>}`.
  It stages nothing. Refusals: a version number the file does not have, `404` `version_not_found`; a
  version that is not `published`, `409` `version_not_published`; the version that is already
  current, `409` `version_is_current`; plus `file_busy`, `file_not_found` and `bad_file_id` as above.

## Done when

- [ ] Replacing a ready file leaves it `ready` and answering from its old content until the worker
      publishes the new version; then it answers from the new content under the new filename.
- [ ] A failed new version leaves the file exactly as it was and says so in `GET /files/{file_id}`.
- [ ] Replacing a failed file runs it through like a new upload.
- [ ] Busy, missing, other-owner and malformed requests are refused as above and stage nothing.
- [ ] `GET /files/{file_id}/versions` lists every version with its outcome, including files that were
      already in the database before the change.
- [ ] Restoring an earlier published version brings its content back as the next version.
- [ ] Tests cover every part; every existing test passes (the exact-body one updated for the two
      keys); `uv run ruff check` and `uv run ruff format --check .` are clean.

## Worked examples

`week-1.pdf` is a `ready` file with chunks from its text "the old lecture text".

| # | Request or event | Result |
|---|---|---|
| 1 | `PUT /files/<id>` with `week-1-v2.pdf` ("the new lecture text") | `202`, body `{"file_id": "<id>", "filename": "week-1-v2.pdf"}` |
| 2 | `GET /files/<id>` right after 1 | `status` `ready`, `replacement` `"pending"`, `replacement_failed_reason` `null`, `filename` `week-1.pdf`; retrieval returns only "the old lecture text" |
| 3 | The worker processes the job from 1 | `status` `ready`, `replacement` `null`, `filename` `week-1-v2.pdf`; retrieval returns only "the new lecture text"; `files.staging_ref` now names the new bytes and the old staged file is still on disk |
| 4 | Instead of 3, the new upload is a corrupt PDF and the worker processes it | `status` `ready`, `failed_reason` `null`, `replacement` `"failed"`, `replacement_failed_reason` `"unparseable"`, `filename` `week-1.pdf`; retrieval returns only the old text; `staging_ref` unchanged |
| 5 | After 4, another `PUT` with a good file | `replacement` `"pending"` and `replacement_failed_reason` `null`; after the worker, the new version is published |
| 6 | `broken.pdf` failed as `unparseable`; `PUT` a good `fixed.pdf` | `status` `queued`, `failed_reason` `null`, `replacement` `null`; after the worker, `ready` as `fixed.pdf` |
| 7 | `GET /files/<id>/versions` after 1 to 3 | `{"versions": [{"version": 2, "filename": "week-1-v2.pdf", "outcome": "published", "failed_reason": null, "current": true}, {"version": 1, "filename": "week-1.pdf", "outcome": "published", "failed_reason": null, "current": false}]}` |
| 8 | The same after 4 instead of 3 | version 2 has `outcome` `"failed"`, `failed_reason` `"unparseable"`, `current` `false`; version 1 is `published` and `current` `true` |
| 9 | A file that was `ready` before this change shipped | its only version is 1, `published`, `current` `true` (a `failed` one: `failed` with its reason; a `queued` one: `pending`) |
| 10 | After 1 to 3, a corrupt `week-1-v3.pdf` fails as version 3; then `POST /files/<id>/versions/1/restore` | `202 {"file_id": "<id>", "filename": "week-1.pdf", "version": 4}`; nothing new in the staging folder; the file stays `ready`, `replacement` `"pending"`, answering from version 2 |
| 11 | The worker processes the job from 10 | the file answers from "the old lecture text" again as `week-1.pdf`; versions: 4 published and current, 3 failed, 2 and 1 published and not current |

## Failure cases that must hold

- `PUT` on a `queued` file, and a second `PUT` while a replacement is pending: `409` `file_busy`, and
  no new file appears in the staging folder.
- `PUT` on an unknown id, and on another owner's file: `404` with exactly the body `GET` returns for an
  unknown id; nothing staged.
- `PUT /files/not-a-uuid`: `400` `bad_file_id`.
- `GET /files/<unknown or other owner's id>/versions`: the same `404` as `GET /files/{file_id}`;
  `GET /files/not-a-uuid/versions`: `400` `bad_file_id`.
- Running the migrations a second time adds no second version 1 to an existing file.
- Restore refusals: version 9 of a file with three versions, `404` `version_not_found`; a failed
  version, `409` `version_not_published`; the current version, `409` `version_is_current`; while a new
  version is pending, `409` `file_busy`.
- A transient provider error on the replacement leaves `replacement` `"pending"` and the old content in
  place; when the retry budget is spent, `replacement` becomes `"failed"` with reason
  `transient_exhausted`, and the old content stays.

## Must not change

- `POST /files`, and the processing of first uploads.
- The four existing keys of the `GET /files/{file_id}` reply and their meaning.
- Every staged file on disk.
- The applied migration files.
- Existing tests, except the exact-body assertion on `GET /files/{file_id}`.
