# Let a student replace an uploaded file with a new version

## Rules that hold for the whole change

Read these first; most of them only bite near the end of the work, in the worker.

1. **A ready file keeps answering until the new version is published.** While a replacement is on its
   way, the file's status stays `ready` (never `queued` or `processing`) and questions are answered
   from its current chunks.
2. **A failed replacement changes nothing.** If the new version fails for any reason (a terminal
   parse failure, or the retry budget running out), the file keeps its current content, chunks,
   filename and status, and `GET /files/{file_id}` says the replacement failed and why.
3. **Nothing staged is deleted.** Staged uploads are kept on purpose (ADR 0010). The file's
   `staging_ref` always points at the bytes its published chunks came from, so it moves to the new
   bytes only when the new version is published.
4. **A refused request stages nothing.** Every refusal below is decided before any bytes are written
   to the staging folder.
5. **The filename changes only on publish.** Until then the file keeps its current name.

## Problem

A student who uploads the wrong version of a lecture, or an updated one, can only upload it again as
a second file, so the class ends up with both versions and answers cite the stale one. There is no
way to give an existing file new contents.

## Why it matters

Students revise their notes during a term. Replacing a file in place keeps the class clean and keeps
every reference to the file's id valid.

## Scope

**In**
- `PUT /files/{file_id}` in `src/gct/api/routers/files.py`, taking the new file as a multipart field
  named `file`, like `POST /files`.
- Whatever the library, queue and worker need for it (`src/gct/files.py`, `src/gct/jobs/`), and a new
  migration if you need to store anything.
- Two new keys in the `GET /files/{file_id}` reply (below), and the committed API snapshot
  `web/openapi.json` (regenerate it with `uv run python web/scripts/openapi_snapshot.py`).
- Tests. An existing test that asserts the exact `GET /files/{file_id}` body may be updated for the
  two new keys; change nothing else in it.

**Out**
- The web client under `web/src/`, including `web/src/api/schema.gen.ts`: do not regenerate it.
- `POST /files` and how a first upload is processed.
- Deleting files, or keeping more than the current and the incoming version.
- Retrieval, the grounder and the answer path.
- The applied migration files (`0001_init.sql`, `0003_failed_reason_too_long.sql`,
  `0004_one_worker.sql`) stay byte-identical.

## Decisions

- **Which files can be replaced:** a `ready` file or a `failed` file. A `queued` or `processing` file,
  or a `ready` file whose replacement is still pending, answers `409` with kind `file_busy`.
- **Owner scoping:** a missing file and another owner's file both answer `404` with kind
  `file_not_found`, the same reply `GET /files/{file_id}` gives for a missing file. A malformed id
  answers `400` with kind `bad_file_id`. Staging refusals (`bad_filename`, `too_large`) are the same
  as for `POST /files`.
- **The reply** to an accepted replacement is `202` with the same body as `POST /files`: `file_id` and
  the new upload's `filename`.
- **A `failed` file** that is replaced is processed like a new upload: it goes back to `queued` with no
  `failed_reason`, then `processing`, then `ready` or `failed`.
- **`GET /files/{file_id}`** always carries two more keys:
  - `replacement`: `"pending"` while a `ready` file's replacement waits to be published, `"failed"`
    when its most recent replacement failed, otherwise `null`;
  - `replacement_failed_reason`: when `replacement` is `"failed"`, the reason (one of the
    `failed_reason` values), otherwise `null`.
- A new replacement clears the record of an earlier failed one.
- A transient provider error is retried as for any upload; while it is retried the replacement stays
  pending.

## Done when

- [ ] Replacing a ready file leaves it `ready` and answering from its old content until the worker
      publishes the new version; then it answers from the new content under the new filename.
- [ ] A failed replacement leaves the file exactly as it was and says so in `GET /files/{file_id}`.
- [ ] Replacing a failed file runs it through like a new upload.
- [ ] Busy, missing, other-owner and malformed requests are refused as above and stage nothing.
- [ ] Tests cover the route and the worker paths; every existing test passes (the exact-body one
      updated for the two keys); `uv run ruff check` and `uv run ruff format --check .` are clean.

## Worked examples

`week-1.pdf` is a `ready` file with chunks from its text "the old lecture text".

| # | Request or event | Result |
|---|---|---|
| 1 | `PUT /files/<id>` with `week-1-v2.pdf` ("the new lecture text") | `202`, body `{"file_id": "<id>", "filename": "week-1-v2.pdf"}` |
| 2 | `GET /files/<id>` right after 1 | `status` `ready`, `replacement` `"pending"`, `replacement_failed_reason` `null`, `filename` `week-1.pdf`; retrieval returns only "the old lecture text" |
| 3 | The worker processes the job from 1 | `status` `ready`, `replacement` `null`, `filename` `week-1-v2.pdf`; retrieval returns only "the new lecture text"; `files.staging_ref` now names the new bytes and the old staged file is still on disk |
| 4 | Instead of 3, the new upload is a corrupt PDF and the worker processes it | `status` `ready`, `failed_reason` `null`, `replacement` `"failed"`, `replacement_failed_reason` `"unparseable"`, `filename` `week-1.pdf`; retrieval returns only the old text; `staging_ref` unchanged |
| 5 | After 4, another `PUT` with a good file | `replacement` `"pending"` and `replacement_failed_reason` `null`; after the worker, the new version is published |
| 6 | `broken.pdf` failed as `unparseable`; `PUT` a good `fixed.pdf` | `status` `queued`, `failed_reason` `null`, `replacement` `null`; after the worker, `ready` as `fixed.pdf` |

## Failure cases that must hold

- `PUT` on a `queued` file, and a second `PUT` while a replacement is pending: `409` `file_busy`, and
  no new file appears in the staging folder.
- `PUT` on an unknown id, and on another owner's file: `404` with exactly the body `GET` returns for an
  unknown id; nothing staged.
- `PUT /files/not-a-uuid`: `400` `bad_file_id`.
- A transient provider error on the replacement leaves `replacement` `"pending"` and the old content in
  place; when the retry budget is spent, `replacement` becomes `"failed"` with reason
  `transient_exhausted`, and the old content stays.

## Must not change

- `POST /files`, and the processing of first uploads.
- The four existing keys of the `GET /files/{file_id}` reply and their meaning.
- Every staged file on disk.
- The applied migration files.
- Existing tests, except the exact-body assertion on `GET /files/{file_id}`.
