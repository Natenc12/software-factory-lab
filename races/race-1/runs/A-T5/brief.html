#9: Cache answers per class: merge brief

PR: Natenc12/pipeline-lab#22, branch a-t5/answer-cache, 1 commit (c770ab5), up to date with main.

Refresher

The problem. answer() asked the provider every time, even when another student in the same class had just asked exactly the same thing. With a real model that is seconds and money per repeat.

The solution. src/lab/ask.py now keeps an in-memory cache. If the same question text was already answered in the same class, and the class's material hasn't changed since, it reuses that answer instead of calling the provider. Each question still gets its own stored answer. clear_answer_cache() empties the cache.

What you chose at the plan. I flagged that a cache keyed on text alone would give one class another class's answer. Reviewer findings

Blocking: none. Scope departures: none. Non-blocking notes Reviewer:

  • Re-saving identical material keeps the cached answer, which is correct under "unchanged material". A teacher re-saving to force a fresh answer won't get one.
  • On a hit, the row records the provider that first produced the answer, not the one passed in (see the calls below).
  • The cache ignores which provider is passed: an answer from one provider is reused when a different one is passed.
  • The key doesn't include which database is open. Two databases in one process with the same class id, material and text would share an entry. That's harmless, because the answer would be identical anyway.
  • The dict has no lock. That's fine with today's single-worker queue.

Calls made without you

  • A hit records the original provider's name. If the cached answer came from provider "fake", the new row says "fake" even when a different provider was passed in, so the row never claims an answer came from a provider that didn't produce it. The ticket says only to store "exactly as on a miss". Low stakes
  • The provider isn't part of the key. This follows your amendment (class + text), which left provider out. It only matters if two providers are used in one process. Today only the fake ships. Should have asked: my plan's option A had the provider in the key and your amendment dropped it without comment, so I am naming it rather than assuming.
  • Test fixture. An autouse fixture in tests/conftest.py empties the cache before and after every test, so tests can't see each other's answers. This was listed in the plan's defaults. Low stakes
  • "Can't find that in the class material" answers are cached like any other answer, until the material changes. This was listed in the plan's defaults. Low stakes

Not checked

  • Not checked Behaviour with a real (slow, paid) model. Only the fake provider exists, so the speed and cost saving is assumed, not measured.

  • Not checked Memory growth in a long-running process. The cache has no size limit, which the ticket rules out of scope, and every material version stays in memory until a restart or clear_answer_cache().
