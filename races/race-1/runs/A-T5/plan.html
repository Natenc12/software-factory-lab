#9: Cache answers by question text

This ends in a pull request (a build, not a spike). Nothing gets merged without your word, and the PR will also need your owner-ok label because src/lab/ask* is a high-risk path.

The ticket, in short

answer() calls the provider every time, even for a question we answered a minute ago. Add an in-memory cache in src/lab/ask.py so a repeat skips the provider, plus clear_answer_cache() and tests. Out of scope: a cache table or migration, expiry or size limits, cache code in the job queue, provider changes, normalising text.

Ticket claims I checked against origin/main (Builder says): answer(conn, question_id, provider=None) exists as described; ask_question strips spaces; the queue path answer_pending calls answer(); no open PR touches ask.py.

One problem with the ticket as written

Keying by question text alone gives wrong answers, and breaks two tests the ticket says must keep passing. Builder says: read from the code, not yet run

The answer depends on three things, not one: the question text, the class's material, and the provider. ask.py's own header says "the same words asked in two classes can get two different answers".

  • Two classes: test_same_question_in_two_classes_gets_each_class_answer asks "Where does energy come from?" in Biology, then in Cooking. With a text-only key, Cooking would get Biology's "Mitochondria produce energy…" instead of "…comes from oats".
  • Material edited: test_answering_again_replaces_the_answer changes the class material and re-answers. With a text-only key it would get the old answer back and never see the new material.

So "key = question text exactly" and "every existing test passes" cannot both hold. This needs your call before I build.

Decision: what the cache is keyed on

A. Text + class material + provider name Recommended

Still keyed by the question text exactly as stored (no lower-casing), but a hit also needs the same material and the same provider. That is precisely what the provider sees, so a cached answer is always the answer the provider would have given.

Then: I build it in ask.py only, every existing test stays untouched and passing, and the merge brief says "You approved key = text; I keyed on text + material + provider".

B. Text only, exactly as the ticket says

CaseBeforeAfter
Ada and Ben both ask "What is DNA?" in Biology2 provider calls1 call
"Where does energy come from?" in Biology, then CookingMitochondria / oatsMitochondria / Mitochondria (wrong class's answer)
Teacher edits Biology material, question re-answeredNew answerOld answer until the process restarts

Then: I would have to rewrite the two tests above to expect the wrong answers (or call clear_answer_cache() inside them to hide it). I don't recommend this.

Not offered: keying on text + class id. Editing the material would then serve stale answers unless classes.set_material cleared the cache, which reaches outside ask.py and the ticket's scope.

Defaults I will use (say if any is wrong)

  • The cache is a module-level dict in src/lab/ask.py; clear_answer_cache() empties it. No table, no migration, no expiry, no size limit.
  • The lookup happens after the hidden/missing checks, so hidden questions still raise exactly as today.
  • On a hit, answer() still writes (or replaces) the answers row with a fresh created_at and the provider's name, and returns it; only the provider call is skipped.
  • A provider error caches nothing (the next try calls the provider again). "Can't find that" answers are cached like any other answer.
  • The queue code is not touched; answer_pending gets the cache through answer().
  • A shared test fixture in tests/conftest.py clears the cache before every test, so tests never see each other's answers.
  • New tests in tests/test_ask.py with a provider that counts its calls: same text twice = 1 call and 2 stored answers; after clear_answer_cache() = called again; the queue path shares the cache; a hidden question is still refused.
