One decision

What do I name the migration file, given PR #13 also adds a 0003?

The migrate script tracks files by full name, so two different 0003_* files both apply and don't clash; they touch different tables. The only cost is a slightly odd-looking history.

A. migrations/0003_last_seen.sql (recommended) — what the ticket asks for. If #13 merges too, the folder holds 0003_last_seen.sql and 0003_streaks.sql; each applies once on every database, in either merge order. Then: I build with this name.
B. migrations/0004_last_seen.sql — keeps numbers unique if #13 lands first, but leaves a gap (no 0003) if it doesn't, and departs from the ticket text. Then: I build with this name and say so in the merge brief.

The plan (defaults I'll use)

  1. New migration (0001 and 0002 untouched): 
    alter table students add column last_seen text;
update students set last_seen =
  (select max(asked_at) from questions q where q.student_id = students.id);
    Hidden questions count (no hidden filter); a student with no questions gets NULL because max() of nothing is NULL.
  2. ask_question: in the same transaction as the insert, before the one commit: 
    update students set last_seen = ?
 where id = ? and (last_seen is null or last_seen < ?)
    So an older asked_at never moves it back. "Later" is compared as text, the same way the backfill's max(asked_at) picks "largest", so the two always agree.
  3. Student: add last_seen: str | None as the last field; from_row fills it. New students start NULL via the column default; enrol_student is unchanged.
  4. Tests: fresh DB migrates twice cleanly; a DB built from only 0001+0002 with data (one student with visible + a later hidden question, one with none) gets only the new file, right backfill, rows kept; ask_question moves forward and not back; get_student(...).last_seen returns the value or None.
  5. Prove: run CI's steps locally, open a draft PR early, independent reviewer agent (this touches the database), then the merge brief.
